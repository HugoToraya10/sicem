1. Introducción y alcance

Este documento describe la arquitectura técnica, el modelo de datos, la interfaz de programación (API) y la infraestructura de despliegue del sistema SICEM (Sistema Integral de Coordinación de Emergencias Médicas), desarrollado para digitalizar la operación del Centro Regulador de Urgencias Médicas (CRUM) de Tabasco, México.

SICEM cubre el ciclo de vida completo de una emergencia médica: recepción de la llamada por el despachador, asignación de una o varias ambulancias, atención en campo por el paramédico (signos vitales, triage, diagnóstico inicial), traslado al hospital destino, recepción y confirmación de llegada por el personal hospitalario, y cierre administrativo — incluyendo el caso interinstitucional, donde una institución solicita en préstamo una ambulancia de otra.

Este manual está dirigido a quien necesite entender o dar mantenimiento al sistema desde el punto de vista técnico: arquitectura, base de datos, contratos de API, y despliegue. Para instrucciones de uso de cada aplicación dirigidas al usuario final, existen manuales de usuario independientes por aplicación (Web/Despachador, Desktop/Hospital, Mobile/Paramédico).

2. Arquitectura general del sistema

SICEM sigue una arquitectura de microservicios: cinco servicios de backend independientes, cada uno responsable de un dominio de negocio acotado, expuestos a través de un gateway único que actúa como punto de entrada HTTP para las tres aplicaciones cliente. Todos los servicios comparten una única base de datos MySQL/MariaDB (sicem), y se comunican entre sí mediante consultas SQL cruzadas directas cuando necesitan datos de otro dominio — un patrón deliberado en este proyecto para mantener la simplicidad, dado su tamaño y equipo de desarrollo, en vez de introducir un bus de mensajería o llamadas HTTP internas servicio-a-servicio.

Puntos clave del diagrama:

  • El gateway (gateway/index.js) es un proxy puro con http-proxy-middleware: no valida tokens, no transforma rutas, solo reenvía cada prefijo (/usuarios, /hospitales, /unidades, /pacientes, /emergencias) al puerto correspondiente.
  • Los tres clientes se conectan al gateway para todo el tráfico REST, pero los sockets se conectan directo a unidades (:3003) y emergencias (:3005), sin pasar por el gateway — cada uno corre su propia instancia independiente de Socket.IO.
  • No existe comunicación HTTP servicio-a-servicio: cuando, por ejemplo, emergencias necesita saber si una ambulancia está disponible, consulta directamente la tabla ambulances vía su propia conexión a la base de datos compartida, en vez de llamar a la API de unidades.
  • El servicio unidades expone un endpoint interno (/unidades/notificar-cierre-sesion) protegido por un secreto compartido (X-Internal-Secret, no un JWT de usuario) que usuarios invoca para forzar el cierre de sesión remoto de un paramédico cuando inicia sesión desde otro dispositivo.

4. Modelo de datos

La base de datos sicem tiene 34 tablas, todas InnoDB con clave primaria numérica autoincremental. Una inconsistencia real y visible del esquema: algunas tablas usan nombres de columna en MAYÚSCULAS y otras en snake_case — no es un error de este documento, así está en la base real (las tablas más recientes, como ambulance_shifts o las de historial clínico, siguen snake_case; las originales del diseño inicial usan mayúsculas).

Patrones de diseño observados en el esquema:

  • Catálogo + tabla operativa: cada entidad operativa (emergencies, ambulances) tiene sus catálogos de tipo/estado como tablas independientes (emergency_types/emergency_statuses, ambulance_types/ambulances_statuses), permitiendo activar/desactivar valores sin borrar historial.
  • Auditoría de historial ligera: patient_allergy_history, patient_condition_history, patient_medication_history y user_credential_history solo registran cambios de is_active + fecha — no versionan todos los campos del registro.
  • user_profiles es el nodo central del modelo: referenciado por prácticamente todas las tablas operativas (emergencias, asignaciones, turnos, notas, expedientes clínicos), representando tanto a empleados del sistema como a pacientes (incluyendo perfiles "No identificado" para pacientes sin identificar en campo).

5. Servicios backend y API

163 endpoints en total, repartidos en 5 servicios detrás del gateway. En todos los servicios, el middleware verifyToken solo valida que el JWT sea válido, que la cuenta esté activa y que la sesión no haya sido invalidada — no existe un middleware de rol genérico; cada controlador valida a mano el rol (y en muchos casos también la institución/registro propio) leyendo req.decoded.

GET POST PATCH — códigos de color usados en las tablas siguientes. público significa sin verifyToken en absoluto.

5.a Gateway (puerto 3000)

Express + cors + http-proxy-middleware. Sin autenticación ni transformación de rutas propia:

app.use('/usuarios',    proxy → http://localhost:3001/usuarios)
app.use('/hospitales',  proxy → http://localhost:3002/hospitales)
app.use('/unidades',    proxy → http://localhost:3003/unidades)
app.use('/pacientes',   proxy → http://localhost:3004/pacientes)
app.use('/emergencias', proxy → http://localhost:3005/emergencias)

7. Autenticación y autorización

La autenticación es stateless vía JWT, firmado con un secreto compartido (JWT_SECRET) entre todos los servicios. Un token contiene el userProfileId, userCredentialId, roleId, y para el rol 3 (paramédico) un sessionId adicional. Expira a las 8 horas.

Middleware verifyToken

Presente (con la misma lógica, duplicada) en cada servicio. Valida, en orden:

  1. Que el header Authorization traiga un JWT válido y no expirado.
  2. Que la credencial referenciada exista en user_credentials y IS_ACTIVE = 1.
  3. Solo para rol 3: que el sessionId del token coincida con active_session_id en la base — si no coincide, la sesión fue invalidada (login desde otro dispositivo) y el token se rechaza aunque su firma sea válida. Los roles 1, 2, 4 y 5 no tienen esta restricción: cualquier JWT con firma válida y credencial activa es aceptado, sin importar si hubo un login posterior desde otro dispositivo.

Autorización por rol

No existe un middleware de autorización por rol. Cada controlador implementa a mano la comparación req.decoded.roleId === N (y frecuentemente también valida que el recurso solicitado pertenezca a la institución o al usuario del token). Esto es válido y funciona correctamente en el sistema actual, pero significa que añadir un nuevo endpoint requiere recordar replicar manualmente esta validación — es un punto de atención para mantenimiento futuro (ver sección 11).

8. Notificaciones push (Firebase Cloud Messaging)

El servicio emergencias integra Firebase Admin SDK para enviar notificaciones push al paramédico cuando SICEM Mobile está en segundo plano o cerrada — principalmente al asignarle una nueva emergencia o al aceptarle una solicitud interinstitucional. El token de dispositivo se guarda por usuario en user_profiles.push_token (endpoint PATCH /usuarios/registrar-push-token).

Las credenciales de la cuenta de servicio de Firebase se cargan de dos formas posibles (config/firebase.js): un archivo local shared/firebase-service-account.json (fuera de cualquier servicio, nunca versionado en git), o la variable de entorno FIREBASE_SERVICE_ACCOUNT_JSON con el JSON completo como texto — pensada para entornos efímeros como GitHub Codespaces, donde no existe forma de persistir un archivo subido manualmente entre reconstrucciones del contenedor. Si ninguna de las dos está presente, el sistema sigue funcionando con normalidad; simplemente no se envían notificaciones push.

10. Infraestructura y despliegue

El backend (gateway + 5 servicios + MySQL) corre en un contenedor de GitHub Codespaces, con los puertos 3000 (gateway), 3003 (socket de unidades) y 3005 (socket de emergencias) reenviados públicamente vía HTTPS. Las credenciales sensibles (contraseña de base de datos, JWT_SECRET, secreto interno entre servicios, credenciales de Firebase) se inyectan como Codespaces secrets — variables de entorno del sistema operativo del contenedor, nunca archivos versionados en el repositorio.

SICEM Web se despliega en Vercel como aplicación estática (build de Vite), con auto-despliegue en cada push a la rama principal del repositorio; sus variables de entorno (VITE_*) apuntan a las URLs públicas del Codespace.

SICEM Desktop y SICEM Mobile se compilan localmente (no hay pipeline de CI/CD para ellas): Electron-builder para el instalador de Windows, y Gradle directo (assembleRelease) para el APK de Android — este último firmado con el keystore de debug incluido en el proyecto, suficiente para distribución interna/de pruebas pero no para publicación en Google Play.

Al ser Codespaces un entorno efímero que se suspende tras inactividad, el backend requiere reanudarse manualmente antes de cada sesión de uso; ver la guía operativa del proyecto para el procedimiento exacto de arranque (MySQL no inicia automáticamente, los 6 procesos Node deben levantarse a mano).

11. Seguridad — hallazgos y áreas de mejora identificadas

Esta sección documenta, con honestidad técnica, brechas reales encontradas en el código actual al elaborar este manual — no son hipotéticas, se verificaron línea por línea contra las rutas y controladores.

Endpoints sin autenticación que deberían requerirla:
  • GET /pacientes/tipos-sangre — no tiene verifyToken, a diferencia de prácticamente todos sus endpoints hermanos en el mismo servicio.
  • GET /usuarios/obtener-usuario-curp/:curp — permite buscar el perfil completo de cualquier persona por CURP sin autenticación alguna. Es el más sensible de los dos: expone datos personales (nombre, teléfono, rol, institución) a cualquiera que conozca o adivine una CURP.
Validación de institución propia ausente en analíticas de emergencias: los endpoints GET /emergencias/analiticas/pacientes-por-tipo/:institutionId, pacientes-por-mes/:institutionId y tiempo-traslado/:institutionId aceptan cualquier institutionId para un usuario Rol 4, sin verificar que sea la institución del propio usuario — a diferencia de sus endpoints hermanos pacientes-en-camino e historial-institucion, que sí hacen esta validación. Un usuario hospitalario autenticado puede consultar analíticas de otra institución cambiando el parámetro de la URL.

Recomendación: agregar verifyToken a los dos endpoints señalados, y replicar en los tres endpoints de analíticas la misma comparación institutionId === req.decoded.institutionId (para Rol 4) que ya existe en sus endpoints hermanos. Ninguno de los tres requiere cambios de esquema ni de contrato de API — son correcciones acotadas al controlador correspondiente.

De forma más general, la ausencia de un middleware de autorización por rol reutilizable (ver sección 7) es la causa raíz de este tipo de inconsistencia: cada nuevo endpoint requiere que quien lo escriba recuerde replicar manualmente la validación correcta, en vez de declararla una sola vez.
